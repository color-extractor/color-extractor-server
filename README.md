# 3. 색상 분석 및 추출 과정

## 웹사이트의 색상을 추출하는 로직은 어떻게 구현 할까?

처음에는 단순히 웹사이트에서 CSS 속성을 가져오면 색상을 분석할 수 있을 것이라 생각했습니다. 하지만 막상 구현을 시작하고 보니, 웹사이트마다 스타일이 적용되는 방식이 다르고, 단순히 색상 값을 가져오는 것만으로는 대표 색상을 도출하기 어려웠습니다.
각 요소에 적용된 색상이 모두 동일한 중요도를 가지는 것도 아니었고, `getComputedStyle()`을 사용해 색상을 추출해도 중복된 데이터, 의미 없는 색상, 투명한 요소 등이 포함되는 문제가 있었습니다. 따라서 중요한 색상만 남기고 대표 색상을 뽑아내는 과정이 필요했습니다.
이를 해결하기 위해 색상 추출 과정을 다음과 같은 네 가지 단계로 정리했습니다.

1. 웹사이트의 스타일 데이터를 크롤링하여 색상 정보를 수집한다.
2. 수집한 색상 데이터를 정제하고 불필요한 색상을 필터링한다.
3. 의미 있는 색상을 판별하여 중요도를 반영한다.
4. 대표 색상을 선정하여 최종 결과로 제공한다.

**크롤링을 통한 웹사이트 색상 데이터 수집**

웹사이트에서 색상을 추출하려면 단순히 CSS 속성을 가져오는 것이 아니라, 실제로 화면에 렌더링된 색상을 정확하게 파악하는 과정이 필요했습니다.하지만 웹사이트마다 스타일 적용 방식이 다르기 때문에, 인라인 스타일에서 색상을 가져오는 것 만으로는 충분하지 않았습니다. CSS 파일에 정의된 색상뿐만아니라 여러 스타일 규칙이 중첩될 때 최종적으로 적용되는 색상까지 모두 고려해야 했습니다. 이를 해결하기 위해 브라우저가 계산한 최종 스타일 값을 가져오는 방식이 필요했고, `getComputedStyle()`을 활용하여 요소별로 실제 적용된 색상을 추출했습니다.

또한, 불필요한 데이터를 줄이기 위해 `display: none`이나 `opacity: 0`처럼 보이지 않는 요소의 색상은 제외하고, 동일한 색상이 반복되는 경우 중복을 줄이는 방식으로 크롤링을 최적화했습니다. 처음에는 iframe이나 Shadow DOM 내부의 스타일까지 포함하려 했지만, Shadow DOM은 접근이 어렵고 일부 웹사이트에서는 `closed` 상태로 설정되어 있어 외부에서 데이터를 가져오는 것이 불가능했습니다. 그래서 현재는 일반적인 DOM을 대상으로 색상을 추출하는 방식으로 구현했습니다.

**수집된 색상 데이터의 정제 및 전처리**

수집된 색상을 대표 색상으로 활용하려면 불필요한 데이터를 제거하고 의미있는 색상을 강조하는 정제 과정이 필수적이었습니다. `getComputedStyle()`을 사용하면 브라우저가 색상을 자동으로 `rgb(r, g, b)` 형식으로 변환해 반환하기 때문에 추가적인 변환 과정은 필요하지 않았습니다. 하지만 불필요한 색상을 걸러내는 것이 중요한 작업이었습니다. 예를 들어, `display: none`이나 `visibility: hidden`이 적용된 요소는 화면에 보이지 않기 때문에 대표 색상을 결정하는 데 영향을 주지 않도록 필터링했습니다. 중복된 색상도 하나로 합쳐야 했습니다. 웹사이트의 CSS 스타일 구조상, `background-color(배경색)`나 `color(텍스트 색상)`처럼 같은 색상이 여러 번 등장하는 경우가 많았기 때문에, 동일한 색상을 여러 개 포함하면 대표 색상을 선정할 때 배경이나 글자로 부터 대표 색상이 추출되는 왜곡이 발생할 수 있었습니다. 따라서 [K-means Clustering](#4-8-k-means-clustering을-이용한-대표-색상-추출-방식과-문제-해결)이라는 군집화 알고리즘을 통해 유사한 색상을 하나로 묶는 과정을 거쳐 분석의 정확도를 높였습니다.

이렇게 정제된 색상 데이터라도 웹사이트에서 모든 색상이 같은 중요도를 가지는 것은 아니기 때문에, 어떤 색상이 더 중요한지를 판별하는 과정이 필요했습니다. 예를 들어, 웹사이트의 배경색과 로고 색상이 같은 비중으로 반영되는 것은 적절하지 않았습니다. 특히, 네비게이션 바 색상처럼 사용자 경험(UX)에 직접적인 영향을 주는 색상이 상대적으로 더 중요하다고 판단했습니다. 또한, 특정 UI 요소에서 사용된 색상을 더 높은 가중치로 반영해야 했습니다. 제목(`h1`), 네비게이션 바(`nav`) 같은 요소에 적용된 색상은 페이지의 핵심적인 부분을 차지하므로, 단순한 구분선이나 작은 아이콘보다 더 높은 우선순위로 처리했습니다. 이렇게 중요도를 고려한 필터링을 통해 색상 데이터에 가중치를 부여하였습니다.

마지막으로, 최종적으로 선정할 대표 색상을 결정하는 과정이 필요했습니다. 단순히 가장 많이 등장하는 색상을 대표 색상으로 지정하는 방식은 적절하지 않았습니다. 예를 들어, 웹사이트의 배경색이 흰색이라면 가장 많이 등장하는 색상이 흰색이 될 수 있지만, 이것이 대표 색상이 될 필요는 없었습니다. 이를 해결하기 위해 [K-means Clustering](#4-8-k-means-clustering을-이용한-대표-색상-추출-방식과-문제-해결) 알고리즘을 활용하여 색상을 그룹화하여 대표 색상을 추출했습니다.

# 4. 구현 세부 사항

## 4-1. 어떻게 하면 웹사이트에서 의미 있는 색상을 찾을 수 있을까?

처음 색상 추출 기능을 개발할 때는 단순히 `getComputedStyle()`을 이용해 웹사이트에서 사용된 모든 색상을 가져오면 된다고 생각했습니다. 하지만 그렇게 가져온 색상 데이터는 너무 많고, 정작 웹사이트를 대표하는 색상을 찾기에는 부적절했습니다.

예를 들어, 웹사이트의 가장 중요한 색상은 로고나 주요 버튼, 제목 등에 사용된 색상이 될 가능성이 높은데, 단순히 등장 빈도만으로 대표 색상을 선정하면 웹사이트의 배경색이나 작은 아이콘의 색상이 대표 색상으로 뽑히는 문제가 발생했습니다. 이렇게 단순 빈도 분석만으로는 의미 있는 색상을 추출하기 어렵다는 점이 큰 도전 과제였습니다. 결국, 모든 색상을 같은 비중으로 다루면 안 되고, 특정 요소에 더 높은 중요도를 부여하는 방식이 필요하다는 결론에 도달했습니다.

### 문제: 웹사이트의 대표 색상으로 의미 없는 색상이 선정되는 문제

```jsx
if (
              propertyValue &&
              (propertyName.includes("color") ||
                propertyName.includes("Color") ||
                propertyName.includes("COLOR") ||
                propertyValue.includes("rgb") ||
                propertyValue.includes("RGB") ||
                propertyValue.includes("!important"))
            ) {
              if (
                allCssPropertiesOfElement.getPropertyValue("display") === "none" ||
                allCssPropertiesOfElement.getPropertyValue("visibility") === "hidden"
              ) {
                continue;
              }

```

이 문제를 해결하기 위해, 먼저 어떤 요소가 중요한지 판단하는 기준을 만들었습니다. h1 같은 요소는 일반 본문 텍스트보다 더 높은 가중치를 가져야 했습니다. 또한, 네비게이션 바, 헤더처럼 웹사이트에서 중요한 역할을 하는 요소의 색상도 우선적으로 고려해야 했습니다. 반대로, `display: none`, `visibility: hidden`처럼 보이지 않는 요소의 색상은 대표 색상 선정에 반영하지 않도록 했습니다. 이런 기준을 설정한 후, 중요한 요소에 가중치를 반영하는 방식으로 데이터를 조정해야 했습니다.

**해결 방법 : 가중치 기반 색상 증강(Augmentation) 기법 적용**

여기서 활용한 개념이 **데이터 증강(Data Augmentation)**이었습니다. 머신러닝분야에서 모델을 개발할 때 특정 데이터를 증강시켜 모델의 학습 효과를 높이는 것처럼, 중요도가 높은 색상을 인위적으로 여러 번 리스트에 추가하여 대표 색상 분석에 더 큰 영향을 미치도록 했습니다. 단순 빈도 기반 분석이 아니라, 디자인적으로 중요한 요소의 색상을 더욱 강조할 수 있도록 데이터를 처리하는 방식입니다.

![Image](https://github.com/user-attachments/assets/bf7e4a6c-3fdf-4817-ae90-6eaa41153b7f)

이 방식을 적용하자, 대표 색상 분석 결과가 훨씬 안정적으로 나왔습니다. 단순히 가장 많이 등장하는 색상이 아니라, 실제로 웹사이트에서 중요한 색상이 대표 색상으로 선정되는 비율이 증가했고, 배경색이 너무 강하게 반영되는 문제도 완화되었습니다. 하지만 여전히 한계는 있었습니다. 웹사이트마다 중요한 요소가 다를 수 있어 특정 요소에 가중치를 부여하는 방식이 항상 적절한 것은 아니었고, 디자인이 단순한 경우에는 배경색이 강하게 반영될 가능성이 있었습니다. 또한, 다크 모드를 지원하는 웹사이트에서는 별도의 처리가 필요했기 때문에, UI 패턴을 자동으로 분석하고, 웹사이트 구조에 따라 가중치를 동적으로 조정하는 방식도 고려할 필요가 있었습니다. 하지만 현재 구현한 방식만으로도 단순히 `getComputedStyle()`로 모든 색상을 가져와서 분석하는 것보다 훨씬 의미 있는 색상 데이터를 도출할 수 있었고, 웹사이트의 핵심 색상을 보다 정확하게 반영할 수 있었습니다.

## 4-2. 웹사이트에서 CSS 데이터 수집의 복잡성

웹사이트의 스타일 데이터를 정확하게 수집하는 것은 예상보다 훨씬 복잡했습니다. 웹사이트마다 CSS가 적용되는 방식이 다르고, 스타일이 여러 계층에서 결정되고, 크롤링을 통해 이를 수집하는 과정에서 다양한 예외 상황이 발생했기 때문입니다. 단순히 `document.querySelectorAll("*")`을 사용해 모든 요소를 선택하고 `getComputedStyle()`을 호출하는 것만으로는 해결되지 않는 문제들이 있었고, 이를 하나씩 해결해 나가야 했습니다.

처음 마주한 문제는 CSS 스타일이 여러 위치에서 정의된다는 점이었습니다. 스타일은 인라인(`style="color: red;"`), 내부 스타일(`style` 태그), 외부 스타일(`link` 태그를 통해 로드된 CSS 파일)에서 정의될 수 있고, 심지어 CSS 변수(`var(--primary-color)`)로 설정되기도 했습니다. 문제는 `getComputedStyle()`을 사용하면 브라우저에서 최종적으로 적용된 스타일만 가져올 수 있어서, 원본 스타일이 어디에서 정의되었는지 알 수 없다는 것이었습니다. 처음에는 CSS 파일을 직접 분석하는 방식도 고려했지만, 웹사이트가 외부 CSS 파일을 여러 개 로드하거나 동적으로 스타일을 변경하는 경우가 많아 실용적이지 않았습니다. 따라서 결국 `getComputedStyle()`을 활용하여 최종 렌더링된 스타일 값을 가져오는 방식을 선택했습니다. 하지만 여기서 또 다른 문제가 있었습니다.

### 문제: css 상속 시, 색상이 중복되는 문제

웹사이트의 스타일은 부모 요소로부터 상속되기도 하고, 특정 조건에 따라 동적으로 변경되기도 합니다. 예를 들어, 텍스트 색상은 부모 요소의 영향을 받을 수 있으며, 다크 모드 지원 웹사이트에서는 `prefers-color-scheme`을 기반으로 스타일이 변경되기도 합니다. 단순히 `getComputedStyle()`을 호출하면 현재 적용된 스타일 값만 가져올 수 있을 뿐, 해당 스타일이 직접 지정된 것인지, 부모 요소에서 상속된 것인지 구별할 수 없었습니다. 이런 문제를 해결하기 위해, 원본 스타일과 비교하여 상속된 스타일을 구별하는 방식을 도입했습니다.

```jsx
const isInheritedColor = (element, propertyName) => {
  if (!element.parentElement) {
    return false;
  }

  const computedStyle = window.getComputedStyle(element);
  const parentStyle = window.getComputedStyle(element.parentElement);

  const inlineStyle = element.style.getPropertyValue(propertyName);

  return (
    computedStyle.getPropertyValue(propertyName) ===
      parentStyle.getPropertyValue(propertyName) && !inlineStyle
  );
};
```

### 해결 방법: 부모 요소와 비교하여 상속된 스타일 필터링

구체적으로, 먼저 `getComputedStyle()`을 사용하여 현재 요소의 스타일을 가져온 후, `element.parentElement`의 `getComputedStyle()` 값을 비교하는 방식으로 접근했습니다. 만약 부모 요소와 같은 `color` 값을 가진다면, 이는 상속된 색상일 가능성이 높았고, 이러한 색상은 대표 색상 추출 과정에서 제외시키는 방식으로 처리했습니다. 하지만 단순히 부모 요소와 동일한 색상이라고 해서 무조건 상속된 값으로 간주할 수는 없었습니다. 어떤 경우에는 자식 요소가 직접 같은 색상을 설정했을 수도 있기 때문입니다. 이를 구별하기 위해 `element.style.color` 값을 추가로 확인하여, 만약 요소의 `style` 속성에서 직접 색상이 지정되지 않았다면 상속된 색상으로 판단하는 방식을 적용했습니다.

## 4-5. CSS 상속 개념을 고려한 색상 추출 방식과 문제 해결

### 4-5-1. css 상속

웹사이트에서 색상을 추출하는 과정에서 가장 까다로웠던 부분 중 하나는 CSS 상속이었습니다. 처음에는 단순히 `getComputedStyle()`을 이용하면 요소별로 적용된 색상을 정확하게 가져올 수 있을 거라 생각했지만, 실제로 구현을 진행하면서 부모 요소에서 상속된 색상과 직접 지정된 색상을 구별하는 것이 필요하다는 점을 깨달았습니다. 예를 들어, 웹사이트의 본문에 적용된 텍스트 색상이 `body` 요소에 설정되어 있는 경우, 해당 색상은 모든 자식 요소에 상속되지만, 개별적인 요소에서 다른 색상을 직접 지정했을 수도 있습니다. 이러한 차이를 무시하고 색상을 분석하면, 실제 웹사이트의 디자인을 반영하지 못하는 대표 색상 분석 결과가 나올 가능성이 높았습니다.

기본적으로 `getComputedStyle()`을 사용하면 브라우저에서 최종적으로 적용된 스타일 값을 반환하기 때문에, 이 값이 부모 요소에서 상속된 것인지, 해당 요소에서 직접 지정된 것인지 구별할 수 없습니다. 즉, 단순히 `getComputedStyle().color` 값을 가져와 분석하면, 상속된 색상까지 그대로 반영될 가능성이 높아지고, 특정 요소에 직접 설정된 색상이 덜 중요하게 취급될 수도 있습니다. 이 문제를 해결하기 위해, 부모 요소와 자식 요소 간의 색상 상속 여부를 구별하는 방법이 필요했습니다.

### 4-5-2. 부모 요소와 색상을 비교하는 방식

가장 먼저 시도한 방법은, 부모 요소의 `getComputedStyle()` 값과 현재 요소의 `getComputedStyle()` 값을 비교하는 방식이었습니다. 만약 두 값이 같다면, 이는 부모 요소로부터 상속된 색상일 가능성이 높다고 판단할 수 있습니다. 하지만 이 방식은 문제가 있었습니다. 특정 요소가 부모와 동일한 색상을 가지고 있더라도, 이는 단순히 같은 색상으로 설정된 것이지 반드시 상속된 색상이라고 단정할 수는 없었기 때문입니다. 예를 들어, `<p>` 요소가 `body` 요소와 같은 색상을 사용한다고 해서, 무조건 `body`에서 상속받았다고 볼 수는 없었습니다.

### 4-5-3. `style` 속성을 확인하여 상속 여부 구별

이 문제를 해결하기 위해, 현재 요소의 `style` 속성을 추가로 확인하는 방식을 도입했습니다. 즉, `element.style.color` 값을 확인하여, 만약 요소가 직접 스타일을 지정한 경우라면, 부모 요소와 동일한 색상이더라도 상속된 것으로 간주하지 않는 방식입니다. 이 방식을 적용하면, 자식 요소가 직접 색상을 지정한 경우와 단순히 상속된 경우를 효과적으로 구별할 수 있었고, 대표 색상을 선정할 때 상속된 색상이 과도하게 반영되는 문제를 해결할 수 있었습니다.

하지만 여기서 또 다른 문제가 있었습니다. CSS 상속에 대해 추가로 학습하는 과정에서 `inherit` 같은 CSS 키워드를 요소의 속성값으로 설정하면 의도적으로 상속받게 할 수도 있다는 점을 알게되었습니다. 또한, CSS 상속과 관련하여 `initial`, `unset`, `revert` 같은 키워드도 존재한다는 것을 확인했습니다. 이런 상황에서 getComputedStyle()을 사용해도 현재 로직은 단순히 style 속성값의 존재 유무만 확인하기 때문에 상속 여부를 정확하게 판별할 수 없었습니다. 그래서 이 부분은 추후에 다양한 CSS 키워드가 설정된 경우를 별도로 처리하는 방식을 추가하여 로직을 개선할 예정입니다.

## 4-6. K-means Clustering을 이용한 대표 색상 추출 방식과 문제 해결

웹사이트에서 색상을 추출한 후, 가장 중요한 과정 중 하나는 대표 색상을 선정하는 것이었습니다. 단순히 가장 많이 등장한 색상을 대표 색상으로 선정하는 방식은 적절하지 않았습니다. 예를 들어, 웹사이트의 배경색이 흰색이라면, 가장 많이 등장하는 색상이 흰색이 될 가능성이 높았지만, 이것이 웹사이트의 대표 색상이라고 보기에는 어려웠습니다. 또한, 텍스트 색상이나 버튼 색상처럼 디자인적으로 중요한 색상들이 대표 색상에서 누락되는 문제도 발생할 수 있었습니다. 이를 해결하기 위해, K-means Clustering을 적용하여 비슷한 색상을 그룹화하고, 가장 의미 있는 대표 색상을 선정하는 방식을 도입했습니다.

### 4-6-1. K-means Clustering이란?

![Image](https://github.com/user-attachments/assets/8b86f7be-f20f-4fc0-b40e-413700747c0c)

K-means Clustering은 데이터 포인트들을 K개의 그룹으로 나누는 비지도 학습 알고리즘으로, 초기에는 K개의 중심점을 랜덤하게 설정한 후, 각 데이터 포인트를 가장 가까운 중심점에 할당하여 클러스터를 형성한 뒤, 각 클러스터의 평균을 계산하여 새로운 중심점을 설정하는 과정을 반복하는 방식으로 작동합니다. 이를 색상 분석에 적용하면 비슷한 색상들을 하나의 그룹으로 묶고, 각 그룹의 대표 색상을 선정할 수 있었습니다.

### 4-6-2. 발생한 문제: K-means의 초기 중심점 설정 문제

**K 값을 어떻게 설정해야 하는가?**

하지만 이를 적용하는 과정에서 몇 가지 문제가 있었습니다. 우선 K 값을 어떻게 설정해야 하는지가 문제였습니다. 현재 대표 색상을 5개로 보여주기 때문에 K 값은 5로 설정되어 있습니다. 하지만 문제가 되는 부분은 웹사이트의 실제 대표 색상이 4개뿐인데 K 값을 5로 설정했을 경우였습니다.

K 값이 실제 필요한 군집 개수보다 크면, 실제로 존재하지 않는 색상까지 대표 색상으로 선정될 가능성이 있습니다. 이로 인해 웹사이트의 주요 색상과 무관한 색상이 추가될 수 있으며, 분석 결과가 왜곡될 위험도 존재했습니다. 반대로, 웹사이트의 대표 색상이 6개 이상인데 K 값을 5로 설정하면, 일부 중요한 색상이 누락될 수도 있습니다. 따라서 K 값을 고정하는 것이 아니라, 웹사이트의 색상 분포에 따라 동적으로 조정하는 방식에 대해서도 고민하고 있습니다.

**초기 중심점 설정에 따라 결과가 달라지는 문제**

또한, K-means는 초기 중심점을 랜덤하게 설정하기 때문에, 실행할 때마다 결과가 달라질 가능성이 있었고, 같은 웹사이트에서도 대표 색상이 달라질 수 있어 일관된 결과를 보장하기 어려웠습니다.

### 4-6-3. 초기 k값 설정 문제 해결을 위한 개선 방향

**K 값 동적 설정**

이 문제를 해결하기 위해 현재는 브랜드 대표 색상을 5개만 보여주도록 K 값을 5로 고정했지만, 웹사이트마다 최적의 K 값이 다를 수 있다는 점을 고려해야 한다고 생각합니다. 그래서 추후에 K 값을 자동으로 조정하는 방식의 도입도 고려하고 있고, 웹사이트의 색상 분포에 따라 엘보우 메서드와 실루엣 점수 같은 기법을 활용하여 최적의 K 값을 찾는 방식도 고려하고 있습니다.

## 4-7. AWS EC2 배포

웹사이트에서 색상을 크롤링하고 분석하는 기능을 AWS EC2 환경에서 배포하는 과정에서 환경 설정 문제로 예상보다 많은 수정이 필요했습니다. 초기에는 단순히 서버 코드를 EC2에 올리고 실행하면 원활하게 동작할 것이라 생각했지만, Puppeteer 실행 환경이 부족해 추가적인 설정이 필요했습니다.

### 4-7-1. Puppeteer가 EC2에서 정상적으로 실행되지 않는 문제

Puppeteer는 기본적으로 Chromium을 내부적으로 실행하여 웹페이지를 렌더링하고 크롤링하는데, EC2와 같은 클라우드 환경에서는 GUI 환경이 없기 때문에, 기본적인 설정만으로는 브라우저가 실행되지 않았습니다. 이를 해결하기 위해, Puppeteer를 실행할 때 `--no-sandbox` 옵션과 `--disable-setuid-sandbox` 옵션을 추가하여 보안 샌드박스 기능을 비활성화하는 방식을 적용했습니다. 또한, EC2 인스턴스에서는 Puppeteer 실행에 필요한 라이브러리가 기본적으로 설치되어 있지 않기 때문에, `chromium`, `libnss3` 등의 필수 패키지를 수동으로 설치해야 했습니다. 이러한 설정을 마친 후에야 Puppeteer가 정상적으로 실행될 수 있었습니다.

### 4-7-2. 배포 과정 개선 및 CI/CD 구축 계획

배포 과정에서도 몇 가지 개선이 필요했습니다. 현재는 수동으로 서버에 코드를 배포하고 실행하는 방식이었지만, 빌드 및 배포 자동화를 위해 Jenkins를 이용한 CI/CD 구축을 계획하고 있습니다. Jenkins를 활용하면 코드 변경 사항이 있을 때 자동으로 빌드하고, EC2에 배포하여 최신 버전의 서버가 항상 운영될 수 있도록 설정할 수 있습니다. CI/CD를 구축하면 배포 과정에서 발생할 수 있는 수동 작업을 줄일 수 있으며, 코드 변경 사항이 반영될 때마다 자동으로 테스트와 배포가 이루어지도록 설정할 수 있습니다. 이를 통해 크롤링 서비스의 유지보수성을 높이고, 코드 변경이 있을 때 더 빠르고 안정적으로 배포할 수 있는 환경을 만들 계획입니다.
